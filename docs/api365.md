ESPECIFICAÇÃO TÉCNICA
Integração GE + 365Scores para consolidação de jogos e transmissões

============================================================
1. OBJETIVO
============================================================

Adicionar o 365Scores como segunda fonte de dados da plataforma,
mantendo o GE como fonte já existente.

O objetivo principal é aumentar a cobertura e a confiabilidade
das informações de transmissão.

A plataforma deverá consolidar informações provenientes de:

1. GE GraphQL
2. 365Scores

Em vez de exibir os dados de cada fonte separadamente, o sistema
deve consolidá-los em um único jogo interno (fixture), evitando
duplicidades.

Exemplo:

GE:
Flamengo x Independiente del Valle
10/09/2026 21:30
Disney+

365Scores:
Independiente del Valle x Flamengo
10/09/2026 21:30
Disney+ / CazéTV

Resultado no produto:

Flamengo x Independiente del Valle
10/09/2026 21:30

Onde assistir:
- Disney+
- CazéTV

O usuário não deve saber de qual fonte cada informação veio,
exceto eventualmente em ferramentas administrativas.


============================================================
2. PRINCÍPIO ARQUITETURAL
============================================================

As fontes externas NÃO devem ser utilizadas diretamente pelo
frontend.

Fluxo obrigatório:

GE
        \
         \
          -> Ingestion -> Normalização -> Matching -> Supabase
         /
365Scores
        /
        ↓
     Next.js
        ↓
     Usuário

O frontend continuará consumindo exclusivamente o banco/API
interno da aplicação.

Não fazer:

Frontend -> GE
Frontend -> 365Scores

Nem:

Frontend -> GE + 365Scores -> merge no cliente


============================================================
3. RESPONSABILIDADE DE CADA FONTE
============================================================

GE:

Responsabilidade principal:
- calendário de jogos;
- times;
- competição;
- fase;
- data;
- horário;
- local;
- transmissões conhecidas pelo GE.

365Scores:

Responsabilidade complementar:
- validação dos jogos;
- identificação de jogos que eventualmente não estejam no GE;
- informações adicionais de transmissão;
- canais de TV;
- plataformas de transmissão;
- transmissões como CazéTV;
- Canal GOAT;
- TNT Sports;
- outras redes identificadas pelo 365Scores.

O 365Scores NÃO deve substituir o GE.

As duas fontes devem ser consideradas independentes.


============================================================
4. NOVO PROVIDER
============================================================

Criar uma implementação de provider para o 365Scores.

Exemplo conceitual:

FootballDataProvider
    ├── GEProvider
    └── Scores365Provider

Responsabilidades:

GEProvider:
    getFixtures()
    getBroadcasts()

Scores365Provider:
    getFixtures()
    getBroadcasts()

A implementação específica de cada fonte deve ficar isolada
do domínio da aplicação.

O restante da aplicação não deve depender de estruturas específicas
do JSON do GE ou do 365Scores.


============================================================
5. ENDPOINT 365SCORES
============================================================

Utilizar como fonte inicial o endpoint:

https://webws.365scores.com/web/games/allscores/

Parâmetros observados:

userCountryId=21

Exemplo:

startDate=10/09/2026
endDate=10/09/2026

A implementação deve encapsular a construção da URL/parâmetros
em um client específico do 365Scores.

Não espalhar URLs ou parâmetros do 365Scores pelo código.


============================================================
6. JANELA DE COLETA
============================================================

Exemplo:

startDate = 10/09
endDate   = 17/09

A janela deve ser configurável.

Não deixar o número "7" hardcoded em diversos pontos do sistema.

Chave lógica:

(provider, external_id)

Essa combinação deve ser única.


============================================================
9. MATCHING ENTRE GE E 365SCORES
============================================================

O sistema deve tentar identificar quando um jogo do 365Scores
corresponde a um fixture já existente no banco.

NÃO comparar apenas pelo ID.

NÃO assumir que IDs das fontes possuem qualquer relação.

O matching deve considerar múltiplos sinais.


------------------------------------------------------------
9.1 TIMES
------------------------------------------------------------

Comparar:

GE home team
GE away team

com:

365Scores homeCompetitor
365Scores awayCompetitor

É necessário manter um mapeamento de times externos.

Tabela:

external_teams

Campos:

id
team_id
provider
external_id
external_name
created_at
updated_at

Exemplo:

team_id | provider   | external_id | external_name
--------|------------|-------------|---------------
10      | GE         | 262         | Flamengo
10      | 365SCORES  | 123         | Flamengo


------------------------------------------------------------
9.2 NORMALIZAÇÃO DE NOMES
------------------------------------------------------------

Não comparar strings literalmente.

Normalizar:

- maiúsculas/minúsculas;
- acentos;
- espaços;
- pontuação;
- abreviações conhecidas;
- nomes alternativos;
- sufixos como FC, SC, EC etc., quando seguro;
- categorias como U20/F quando fizer sentido.

Exemplo:

"Flamengo"
"CR Flamengo"
"Flamengo FC"

podem ser candidatos ao mesmo time.

Porém, NÃO remover informações que diferenciem equipes.

Exemplo:

"Brasil"
"Brasil Sub-20"
"Brasil Feminino"

não devem ser automaticamente tratados como o mesmo time.


------------------------------------------------------------
9.3 ORDEM DOS TIMES
------------------------------------------------------------

O matching deve considerar que:

GE:
Independiente del Valle x Flamengo

365Scores:
Flamengo x Independiente del Valle

pode representar a mesma partida caso outras evidências
confirmem o vínculo.

Portanto, testar:

mandante + visitante

E também:

visitante + mandante

quando necessário.


------------------------------------------------------------
9.4 DATA
------------------------------------------------------------

Comparar a data local da partida.

A timezone principal do produto é:

America/Sao_Paulo

O startTime do 365Scores possui offset.

Converter para o timezone do produto antes da comparação.


------------------------------------------------------------
9.5 HORÁRIO
------------------------------------------------------------

Comparar horário de início.

Utilizar tolerância configurável.

Sugestão inicial:

± 30 minutos

Não utilizar tolerância excessivamente grande.

O horário é um sinal de matching, não necessariamente a única
condição.


------------------------------------------------------------
9.6 COMPETIÇÃO
------------------------------------------------------------

Usar competição como sinal adicional.

Exemplo:

GE:
Libertadores

365Scores:
Taça Conmebol Libertadores

Considerar normalização/mapeamento.

Não exigir igualdade textual.

A competição pode ajudar a aumentar a confiança do matching.


============================================================
10. SCORE DE MATCHING
============================================================

Recomenda-se utilizar um score.

Exemplo inicial:

Times correspondentes:
+60

Data correspondente:
+20

Horário compatível:
+15

Competição compatível:
+5

Total:
100

Matching automático:

>= 90
    -> vincular automaticamente

70-89
    -> candidato / revisão

< 70
    -> não vincular automaticamente

Esses valores devem ser configuráveis.

O sistema deve registrar o score e os critérios utilizados
para facilitar diagnóstico.


============================================================
11. CASOS ESPECIAIS DE MATCHING
============================================================

Considerar:

- mando invertido;
- mudança de horário;
- jogo adiado;
- nomes diferentes;
- competições com nomes diferentes;
- partidas de categorias de base;
- partidas femininas;
- amistosos;
- jogos com nomes abreviados.

Nunca realizar matching agressivo quando houver risco de associar
uma transmissão ao jogo errado.

É preferível deixar uma transmissão sem vínculo automático do que
associá-la incorretamente.


============================================================
12. TRANSMISSÕES DO 365SCORES
============================================================

O principal campo inicial será:

hasTVNetworks

e:

tvNetworkName

Exemplos:

"CazéTV"

"TNT Sports/HBO Max/Youtube TNT Sports"

"Globo"

"Premiere"

etc.

Se:

hasTVNetworks = false

não criar uma transmissão.

Se:

hasTVNetworks = true

processar tvNetworkName.


============================================================
13. NORMALIZAÇÃO DE TV NETWORKS
============================================================

O campo tvNetworkName pode conter várias plataformas/canais.

Exemplo:

"TNT Sports/HBO Max/Youtube TNT Sports"

NÃO armazenar necessariamente isso como um único BroadcastSource.

Separar os itens quando houver delimitadores reconhecidos.

Resultado esperado:

TNT Sports
HBO Max
YouTube TNT Sports

O parser deve ser configurável.

Não fazer split indiscriminado em qualquer caractere.

17. MODELO RECOMENDADO PARA MÚLTIPLAS FONTES
============================================================

============================================================
18. PRIORIDADE ENTRE FONTES
============================================================

Quando as duas fontes apresentarem informações diferentes,
não sobrescrever automaticamente uma com a outra.

Manter as evidências.

Exemplo:

GE:
Premiere

365Scores:
CazéTV

Resultado:

Premiere
CazéTV

O sistema deve assumir que ambas podem estar corretas.

Somente remover uma transmissão quando houver uma regra explícita
ou evidência suficiente de que ela deixou de existir.


============================================================
19. TRANSMISSÃO AUSENTE
============================================================

É fundamental diferenciar:

A) Não existe informação de transmissão

de:

B) Não existe transmissão.

Se GE não possui transmissão e 365Scores também não possui:

mostrar:

"A transmissão ainda não foi divulgada."

Não mostrar:

"Não há transmissão."


============================================================
20. ATUALIZAÇÃO DE DADOS
============================================================

A ingestão deve ser idempotente.

Executar a mesma coleta várias vezes não deve criar:

- partidas duplicadas;
- times duplicados;
- competições duplicadas;
- transmissões duplicadas;
- external_matches duplicados.

365Scores:

upsert por:

que o jogo já existe.

22. STATUS DA PARTIDA
============================================================

O 365Scores fornece:

statusGroup
statusText
shortStatusText

status do 365Scores.

Criar uma estratégia de normalização.

Exemplo interno:

CANCELLED

Mapear os status externos para esses valores.


============================================================
23. DADOS DO JOGO
============================================================

O GE continua sendo a principal referência para a estrutura do
jogo quando disponível.

365Scores pode atuar como validação/complemento.

Se o jogo existir somente no 365Scores, ele poderá ser criado,
desde que passe pelas regras de qualidade/matching necessárias.

Esse comportamento deve ser configurável.


============================================================
24. JOGOS EXISTENTES SOMENTE NO 365SCORES
============================================================

Caso o 365Scores encontre um jogo que não exista no GE:

1. tentar localizar por time/data/competição;
2. se não encontrar:
   criar candidato;
3. validar se a competição está habilitada;
4. validar se é futebol;
5. validar se pertence ao escopo da plataforma;
6. criar fixture somente se passar pelas regras.

Não criar indiscriminadamente todos os jogos retornados pelo
365Scores.

Especial atenção para:

- futebol feminino;
- categorias de base;
- amistosos;
- competições menores;
- modalidades que eventualmente apareçam por erro de filtro.


============================================================
25. FILTRO SPORT
============================================================

Utilizar:

sportId = 1

como filtro inicial para futebol.

Mesmo assim, validar o valor durante a ingestão.

Não assumir que qualquer resposta futura continuará com o mesmo
formato sem validação.


============================================================
26. onlyOnTv
============================================================

Utilizar:

onlyOnTv=true

para a coleta específica de transmissões.

Isso reduz a quantidade de jogos irrelevantes para essa finalidade.

Porém, não utilizar esse endpoint como única fonte do calendário
se a plataforma precisar de partidas que não possuem transmissão
informada.

O calendário principal continua sendo responsabilidade do GE.

============================================================
32. YOUTUBE API
============================================================

A YouTube API NÃO faz parte da integração obrigatória desta fase.

Motivo:

ela pode encontrar uma live futura somente depois que a transmissão
for criada/agendada no YouTube.

Ela não resolve a descoberta antecipada do direito de transmissão.

Exemplo:

09/09:
365Scores -> CazéTV

YouTube:
nenhuma live agendada

A plataforma ainda deve mostrar:

CazéTV

Posteriormente, a YouTube API poderá ser usada como enriquecimento
para localizar a URL específica da transmissão.

Isso deve ser considerado uma futura melhoria.

46. CRITÉRIOS DE ACEITE
============================================================

A implementação será considerada concluída quando:

[ ] GE continuar funcionando exatamente como antes.

[ ] 365Scores estiver integrado como segunda fonte.

[ ] Nenhum ID externo for utilizado como ID interno do fixture.

[ ] Cada jogo do 365Scores puder ser associado ao fixture interno.

[ ] Matching funcionar mesmo com mandante/visitante invertidos.

[ ] Times possuírem external_teams por provider.

[ ] Transmissões do 365Scores forem normalizadas.

[ ] "CazéTV" for reconhecida como BroadcastSource.

[ ] "Canal GOAT" for reconhecido como BroadcastSource.

[ ] Múltiplas redes em tvNetworkName forem separadas.

[ ] GE + 365Scores não produzirem transmissões duplicadas.

[ ] Ausência de transmissão não for interpretada como
    "não existe transmissão".

[ ] Todas as operações forem idempotentes.

[ ] Falhas do 365Scores não derrubarem a aplicação.

[ ] Falhas do GE não derrubarem a aplicação.

[ ] Logs da ingestão estiverem disponíveis.

[ ] Métricas básicas da ingestão estiverem disponíveis.

[ ] Frontend continuar consumindo somente o banco interno.

[ ] Páginas dinâmicas continuarem funcionando sem alteração
    de URL.

[ ] O produto conseguir exibir uma transmissão encontrada
    exclusivamente pelo 365Scores.

Real Madrid x Rayo Vallecano
12/09/2026

Se 365Scores informar:

CazéTV

e GE não informar CazéTV,

o produto deverá exibir:

CazéTV

na página do jogo.


============================================================
47. TRATAMENTO DE FALHAS
============================================================

Se o 365Scores estiver indisponível:

- não apagar dados existentes;
- manter última informação válida;
- registrar erro;
- continuar disponibilizando o produto.

Se o GE estiver indisponível:

- mesma estratégia.

Nenhuma fonte externa deve ser um ponto único de falha
para a disponibilidade do site.
